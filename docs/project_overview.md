# 공정감사위원회 업무 자동화 시스템 개요

## 1. 프로젝트 배경

세종대학교 공정감사위원회는 50개 이상의 자치 기구들로부터 결산안과 통장거래내역을 제출받아, 학생회비가 공정하고 투명하게 사용되었는지를 사무감사교육자료에 따라 검토합니다. 감사 과정에서는 결산안과 통장거래내역의 형식, 거래 일치 여부, 증빙자료의 적합성, 규정 위반 여부 등을 종합적으로 확인해야 하며, 규정을 지키지 않은 경우에는 교육자료와 징계 기준에 따라 벌점이 부과됩니다.

또한 감사는 1차, 2차, 3차로 나뉘어 진행되며, 1차와 2차에서는 시정 기회가 주어지고, 3차 이후에도 시정되지 않은 항목에 한해 벌점이 확정됩니다. 즉 이 업무는 단순 검토가 아니라, 규정 해석, 거래 대조, 증빙 확인, 차수별 처리 기준까지 동시에 적용해야 하는 다층적 업무입니다.

이 프로젝트는 이러한 반복적이고 복잡한 감사 업무를 자동화하기 위해 시작되었습니다.

---

## 2. 자동화 필요성

현재의 감사 방식은 사람이 직접 결산안과 통장거래내역, 증빙자료를 하나씩 대조하며 판단하는 구조입니다. 이 방식은 정확성이 중요하다는 장점이 있지만, 동시에 많은 시간과 인력이 필요하고, 동일한 규정을 반복적으로 적용하는 과정에서 피로와 편차가 발생할 수 있습니다.

특히 공정감사 업무는 단순히 표 안의 숫자만 보는 것이 아니라 다음 세 가지를 동시에 검토해야 합니다.

1. 형식이 맞는가  
2. 거래가 맞는가  
3. 증빙이 맞는가  

이는 마치 세 겹의 체로 자료를 걸러내는 과정과 같습니다. 첫 번째 체는 형식, 두 번째 체는 숫자, 세 번째 체는 영수증입니다. 사람이 이 세 층을 모두 반복적으로 확인하는 구조는 필연적으로 비용이 큽니다. 따라서 자동화 도구는 단순 편의 기능이 아니라, 감사의 일관성과 효율성을 높이기 위한 핵심 수단입니다.

---

## 3. 프로젝트 목표

이 프로젝트의 목표는 사무감사교육자료에 명시된 규정을 기계가 판정 가능한 조건으로 번역하여, 결산안과 통장거래내역, 그리고 증빙자료를 자동으로 검토하는 시스템을 구축하는 것입니다.

사용자는 자동화 도구에 두 개의 엑셀 파일을 업로드합니다.

- 월별 결산안
- 통장거래내역

시스템은 교육자료 기준에 따라 해당 파일을 검토하고, 다음과 같은 결과를 제공합니다.

- 몇 행의 어떤 열이 잘못되었는지
- 왜 잘못되었는지
- 어떤 규정을 근거로 판단했는지
- 관련 교육자료 페이지가 어디인지
- 어떻게 수정해야 하는지
- 3차 기준 예상 벌점이 몇 점인지

즉 이 프로젝트의 목표는 단순한 오류 탐지기가 아니라, **감사위원이 작성하는 답안지 형식의 설명형 리포트**를 자동으로 생성하는 것입니다.

---

## 4. 프로젝트의 핵심 개념

이 시스템은 단순히 파일을 읽는 프로그램이 아닙니다.  
이 프로젝트의 본질은 **규정을 판정 가능한 조건으로 번역하는 시스템**입니다.

교육자료는 다음과 같은 요소들을 세부적으로 규정합니다.

- 파일명 형식
- 시트명 형식
- 시트 보호 여부
- 엑셀 수식 사용 여부
- 통장거래내역 정렬 방식
- 증빙자료명 표준
- 거래 유형별 필요 증빙 조합
- 벌점 구조
- 감사 차수별 처리 기준

즉 이 프로젝트는 “엑셀 파일을 여는 도구”가 아니라, **규정 기반 감사 엔진 + 거래 매칭 엔진 + 증빙 판독 엔진 + 벌점 산정 엔진**이 결합된 시스템으로 이해해야 합니다. 법전을 코드로 번역하는 작업에 가깝고, 표면적으로는 파일 검토지만 실제로는 규칙 집행 시스템에 해당합니다.

---

## 5. 전체 시스템 구조

시스템은 크게 입력, 전처리, 감사 엔진, 출력의 네 단계로 구성됩니다.

### 5.1 입력

사용자는 다음 자료를 업로드합니다.

- 결산안 엑셀 파일
- 통장거래내역 엑셀 파일
- 필요 시 추가 증빙 파일 또는 원본 압축파일

교육자료상 결산안과 통장거래내역은 함께 제출되어야 하며, 결산안의 증빙은 셀의 노트(메모)에 이미지를 삽입하는 방식으로 첨부됩니다. 따라서 이 시스템은 표 데이터뿐 아니라, 엑셀 내부에 숨겨진 이미지 자산까지 함께 다뤄야 합니다.

### 5.2 전처리

업로드된 파일에서 먼저 다음 요소를 읽습니다.

- 파일명
- 시트명
- 보호 여부
- 시트 구조
- 셀 값
- 수식 존재 여부
- 노트(메모) 존재 여부
- 노트에 삽입된 이미지 자산

이 단계의 핵심은, 일반적인 데이터프레임 처리만으로는 충분하지 않다는 점입니다. 증빙이 노트 이미지로 들어가므로, 엑셀 내부 구조를 직접 탐색하고 이미지와 메타 정보를 추출할 수 있어야 합니다.

### 5.3 감사 엔진

감사 엔진은 크게 네 개의 모듈로 나뉩니다.

1. 형식 규칙 엔진
2. 거래 매칭 엔진
3. 증빙 판독 엔진
4. 벌점 엔진

### 5.4 출력

최종적으로 시스템은 다음 정보를 포함한 결과를 사용자에게 제공합니다.

- 문제 발생 위치
- 위반 규칙
- 문제 설명
- 규정 근거
- 관련 교육자료 페이지
- 수정 방법
- 차수별 안내 문구
- 3차 기준 예상 벌점 총점

즉 출력은 단순 오류 목록이 아니라, 사람이 이해하고 바로 수정에 활용할 수 있는 설명형 감사 결과물이어야 합니다.

## 6. 감사 구조: 3단계 구조

사람 감사위원의 실제 업무를 기준으로 보면, 감사는 세 층으로 나눌 수 있습니다.

### 6.1 1단계: 형식 감사

가장 먼저 확인하는 것은 형식입니다.

- 파일명이 맞는가
- 시트명이 맞는가
- 시트 보호가 적용되었는가
- 수식이 제대로 들어가 있는가
- 통장거래내역 정렬이 맞는가
- 불필요한 행이나 과도한 셀 병합이 없는가

형식 감사는 가장 먼저, 가장 낮은 비용으로 잡아낼 수 있는 문제를 처리하는 단계입니다. 현관문에서 신발의 흙을 먼저 털어내는 과정과 비슷합니다. 초기에 형식 오류를 정리하면 이후 단계의 정확도도 높아집니다.

### 6.2 2단계: 거래 감사

그다음은 장부와 은행 원장이 실제로 일치하는지 확인하는 단계입니다.

- 날짜가 맞는가
- 금액이 맞는가
- 입금/출금 방향이 맞는가
- 거래처명이 유사한가
- 잔액 흐름이 자연스러운가
- 전월이월금/전기이월금이 논리적으로 이어지는가
- 누락된 거래가 없는가

이 단계는 퍼즐 맞추기와 같습니다. 결산안의 조각 하나마다 통장이라는 원본 조각이 있어야 하며, 1:1 완전 일치뿐 아니라 현실적인 허용 오차를 고려한 매칭 로직이 필요합니다.

### 6.3 3단계: 증빙 감사

마지막은 영수증과 각종 증빙의 존재 및 적합성을 확인하는 단계입니다.

- 증빙 노트가 존재하는가
- 노트 안에 이미지가 존재하는가
- 이미지가 읽을 수 있는 품질인가
- 어떤 문서 종류인가
- 거래 유형에 맞는 증빙 조합인가
- 날짜, 금액, 거래처, 승인번호, 수량 등 핵심 필드가 맞는가

거래 매칭이 뼈대라면, 증빙 감사는 엑스레이에 가깝습니다. 겉으로는 맞아 보여도, 실제 서류가 없거나 필요한 정보가 누락되어 있으면 규정상 문제가 됩니다.

### 6.4 최종 단계: 벌점 및 결과 리포트

마지막으로 시스템은 차수와 규칙에 따라 결과를 정리합니다.

- 1차/2차: 시정사항 중심 안내
- 3차: 예상 벌점 산정 포함

여기서 중요한 점은, 모든 위반을 무조건 FAIL로 처리하는 것이 아니라, 확정 위반, 검토 필요, 판정 불가를 구분해야 한다는 점입니다. 예를 들어 암호가 걸린 파일, 이미지 추출 실패, OCR 실패는 규정 위반이 아니라 기술적 한계일 수 있으므로 별도 상태로 관리해야 합니다.

## 7. 주요 모듈 설명

### 7.1 형식 감사 모듈

형식 감사 모듈은 다음 항목을 자동으로 검사합니다.

- 결산안 파일명 패턴
- 통장거래내역 파일명 패턴
- 시트명
- 시트 보호 여부
- 수식 사용 여부
- 불필요한 행 존재 여부
- 셀 병합 과다 여부
- 통장거래내역 정렬 방향
- 암호로 인한 확인 불가 상태

이 모듈은 구현 난도가 비교적 낮고 정확도가 높아, 초기 MVP 단계에서 가장 먼저 구현하기 적합합니다.

### 7.2 거래 매칭 모듈

거래 매칭 모듈은 결산안과 통장거래내역을 대조합니다.

- 날짜 근접 매칭
- 금액 일치
- 입출금 방향 일치
- 거래처명 유사도 매칭
- 잔액 흐름 검증
- 전월이월금/전기이월금 연결 검증
- 누락 거래 탐지

감사의 중심은 결국 장부와 원장이 맞는가에 있기 때문에, 이 모듈은 시스템의 핵심 축 중 하나입니다.

### 7.3 증빙 판독 모듈

증빙 판독 모듈은 노트 이미지 기반 증빙 검토를 담당합니다.

1. 노트가 달린 셀 위치 추출
2. 이미지 자산 추출
3. OCR 수행
4. 문서 종류 분류
5. 핵심 필드 추출
6. 결산안 거래행과 연결
7. 규칙 엔진에 전달

현재까지의 프로토타입에서는 표 데이터와 거래 데이터 중심 검증이 우선이지만, 최종 시스템은 반드시 노트 이미지 추출과 증빙 판독 기능을 포함해야 합니다. 이 부분이 빠지면 반자동 도구는 될 수 있어도, 실사용 가능한 Level 2 자동화 도구가 되기는 어렵습니다.

### 7.4 벌점 엔진

벌점 엔진은 차수와 위반 규칙에 따라 결과를 정리합니다.

- 1차/2차: 시정 중심
- 3차: 예상 벌점 산정
- 규칙별 벌점 누적
- 동일 유형 중복 처리 기준 반영
- FAIL / REVIEW / BLOCKED 구분

감사의 결과는 단순히 “틀렸다”가 아니라, “어떤 조치를 해야 하는가”로 연결되어야 하므로 벌점 엔진은 결과 리포트의 실용성을 결정하는 모듈입니다.

## 8. 권장 기술 스택

[고유의 의견]  
이 프로젝트의 목적을 고려했을 때 가장 안정적인 기술 구조는 **Python 백엔드 + 규칙 DB(JSON/YAML/CSV) + OCR + 간단한 웹 UI**입니다.

권장 스택은 다음과 같습니다.

- **백엔드**: Python
- **엑셀 분석**: openpyxl
- **표 데이터 처리**: pandas
- **노트/이미지 추출**: openpyxl + 압축 구조 분석 + 필요 시 XML 파싱
- **OCR**: 로컬 OCR 또는 API 기반 OCR
- **규칙 데이터베이스**: JSON / YAML / CSV
- **결과 저장**: SQLite 또는 CSV
- **UI**: Streamlit

이 프로젝트는 화려한 화면보다 안정적인 규칙 처리와 결과 생성이 더 중요합니다. 스포츠카보다 작업용 트럭이 필요한 문제에 가깝습니다.

## 9. 개발 로드맵

### 9.1 1단계: 형식 감사 MVP

가장 먼저 구현해야 하는 것은 형식 검사기입니다.

- 파일명
- 시트명
- 시트 보호
- 수식 사용 여부
- 정렬 방향
- 암호 확인

이 단계는 규정 근거가 명확하고 자동화 정확도도 높기 때문에, 가장 빠르게 가시적인 성과를 낼 수 있습니다.

### 9.2 2단계: 거래 매칭 엔진

다음 단계는 결산안과 통장거래내역 간 자동 대조입니다.

- 누락 거래
- 금액 불일치
- 날짜 불일치
- 잔액 흐름 이상

이 단계까지 구현되면 사람 감사의 상당 부분이 자동화됩니다.

### 9.3 3단계: 증빙 존재 확인

처음부터 완전한 OCR 판독으로 가기보다, 먼저 다음을 확인하는 단계로 확장합니다.

- 노트 존재 여부
- 이미지 추출 여부
- 증빙자료명 존재 여부

### 9.4 4단계: OCR 기반 증빙 판독

그다음에 실제 영수증 정보 추출과 문서 유형 분류로 확장합니다.

### 9.5 5단계: 벌점 및 결과지 생성

## 10. 감사 규칙 데이터베이스 방향

이 프로젝트에서 사용할 감사 규칙 데이터베이스는 단순 메모장이 아니라, 코드가 직접 읽고 실행할 수 있는 구조여야 합니다.

권장 필드는 다음과 같습니다.

- `rule_id`
- `category_lv1`
- `category_lv2`
- `rule_name`
- `description`
- `trigger_condition`
- `check_logic`
- `required_fields`
- `required_evidence`
- `pass_condition`
- `fail_condition`
- `penalty_points`
- `penalty_stage`
- `exception_rule`
- `manual_review_needed`
- `source_page`
- `source_text_summary`

즉 규칙 하나는 단순 문장이 아니라, 기계가 판정 가능한 최소 단위여야 합니다. 법전을 코드로 바꾸는 과정처럼, 사람이 읽는 조문을 프로그램이 집행할 수 있는 데이터 구조로 변환해야 합니다.

---

## 11. 평가 가능성 및 확장성

이 프로젝트의 강점 중 하나는 실제 감사 결과 데이터가 많이 존재한다는 점입니다. 과거 결산안, 통장거래내역, 증빙자료, 그리고 실제 감사 결과(답안지)를 비교하면, 시스템이 얼마나 정확하게 규칙을 판정하는지 채점 방식으로 평가할 수 있습니다.

즉 이 프로젝트는 단순한 자동화 구현에서 끝나지 않고, 다음과 같은 방향으로 확장 가능합니다.

- 규칙별 정확도 평가
- 자동/반자동/수동검토 비율 분석
- OCR 품질에 따른 성능 분석
- 감사 단계별 오류 유형 통계
- 규칙 엔진 개선 우선순위 도출

이 점은 프로젝트를 단순 도구가 아니라, 평가 가능한 시스템으로 만든다는 점에서 중요합니다.

## 12. 최종 결론

이 프로젝트가 지향하는 최종 동작 흐름은 다음과 같습니다.

**업로드 → 형식 감사 → 거래 매칭 → 증빙 추출 → OCR 판독 → 규칙 판정 → 차수별 결과 출력 → 3차 예상 벌점 산정**

이 흐름은 실제 사무감사교육자료가 요구하는 감사 방식과 가장 가깝습니다.  
결산안과 통장거래내역의 업로드, 시트 보호와 수식 확인, 증빙 노트 이미지 첨부, 거래 유형별 증빙 조합, 감사 차수, 벌점 체계까지 모두 이 구조 안에 자연스럽게 포함됩니다.

즉 이 설계는 단순한 아이디어가 아니라, 이미 존재하는 감사 규정을 프로그램의 동작 순서로 번역한 결과입니다.  
이 프로젝트의 본질은 파일을 읽는 프로그램이 아니라, **규정을 실행 가능한 조건으로 번역하는 감사 자동화 시스템**에 있습니다.
